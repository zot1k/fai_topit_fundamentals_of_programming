## 2. Задание 1. Имена, ссылки и изменяемость

### Эксперимент A. Неизменяемый объект (`int`)
```python
a = 10
b = a
a += 1
```

* **Прогноз:** Изначально `a` и `b` ссылаются на один и тот же объект `10` (`id(a) == id(b)`). После `a += 1` переменная `a` начнет ссылаться на новый объект `11`, а `b` останется связанной с `10`.
* **Фактический результат:**
  - До `a += 1`: `a = 10, b = 10`, `id(a) == id(b)` (например, `140571147515648`).
  - После `a += 1`: `a = 11, b = 10`, `id(a)` изменился, `id(b)` остался прежним.
* **Объяснение:** Объекты типа `int` является неизменяемыми (`immutable`). Оператор `+=` для `int` не модифицирует существующий объект в памяти, а вычисляет новое значение, создает объект `11` и связывает имя `a` с этим новым объектом. Имя `b` при этом продолжает указывать на прежний объект `10`.

### Эксперимент B. Изменяемый объект (`list`)
```python
first = [10, 20]
second = first
second.append(30)
```

* **Прогноз:** Поскольку список — изменяемый объект (`mutable`), `first` и `second` указывают на один и тот же список в памяти. Вызов `second.append(30)` изменит список по месту, что отразится и при обращении через `first`.
* **Фактический результат:**
  - `first` и `second` до append: `[10, 20]`, `id(first) == id(second)`.
  - После `second.append(30)`: `first = [10, 20, 30]`, `second = [10, 20, 30]`. `id` объектов не изменились.
  - Переназначение `second = [10, 20, 30]`: приводит к созданию нового списка. `first == second` дает `True`, но `first is second` дает `False`. Дальнейший `second.append(40)` никак не влияет на `first`.

#### Схемы связей между именами и объектами (до и после переназначения `second`):

**1. До переназначения (`second = first`, после `append(30)`):**
```text
  Имя            Объект в памяти
[ first  ] ----\
                +---> [ List: [10, 20, 30] ] (id: 0x7f...00)
[ second ] ----/
```

**2. После переназначения (`second = [10, 20, 30]`, затем `second.append(40)`):**
```text
  Имя            Объект в памяти
[ first  ] ---------> [ List: [10, 20, 30] ]     (id: 0x7f...00)

[ second ] ---------> [ List: [10, 20, 30, 40] ] (id: 0x7f...99)
```

### Эксперимент с последовательным копированием
В `task_2.py` прослежена динамика объектов при операциях `alias = original`, `shallow = original.copy()` и `deep = copy.deepcopy(original)`.

#### Таблица наблюдений:

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|---|---|---|---|
| **Присваивание (`alias`)** | Нет (`id` совпадает) | Нет (`id` совпадает) | **Нет** (все изменения общие) |
| **Поверхностная копия (`shallow`)** | **Да** (новый внеш. список) | Нет (`id` вложенных тот же) | **Частично** (добавление в внешний список независимо; изменение элементов во вложенном списке меняет обе структуры) |
| **Глубокая копия (`deep`)** | **Да** (новый внеш. список) | **Да** (новые вложенные объекты) | **Да** (полная независимость всех уровней) |

### Исследование ошибочного создания матрицы
При создании матрицы `wrong_matrix = [[0] * 3] * 3`:
- Умножение списка `[* 3]` производит поверхностное копирование внешнего списка. В результате все три строки являются **ссылками на один и тот же внутренний список** `[0, 0, 0]`.
- Операция `wrong_matrix[0][0] = 1` изменяет этот единственный внутренний список, превращая матрицу в `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`.
- При правильном создании через генератор списков `correct_matrix = [[0] * 3 for _ in range(3)]` на каждой итерации цикла конструируется уникальный объект списка, что подтверждается разностью `id(row 0)`, `id(row 1)` и `id(row 2)`.

### Ответы на вопросы для анализа (Задание 2)
1. **Чем поверхностная копия отличается от глубокой?**  
   Поверхностная копия создает новый контейнер, но заполняет его ссылками на те же самые внутренние элементы. Глубокая копия рекурсивно дублирует как сам контейнер, так и все вложенные изменяемые объекты.
2. **Почему глубокое копирование не следует применять автоматически ко всем объектам?**  
   Глубокое копирование создаёт ощутимые накладные расходы по времени выполнения и памяти, а также может приводить к зацикливанию при наличии рекурсивных связей (хотя `copy.deepcopy` и использует внутренний словарь `memo`).
3. **В каких случаях достаточно поверхностной копии?**  
   Когда структура является плоской (одноуровневой) или когда вложенные элементы являются неизменяемыми (`int`, `str`, `tuple`, `frozenset`).

## 4. Задание 3. Подсчет ссылок и слабые ссылки

### Эксперимент с `sys.getrefcount()`
Результаты вызовов в `task_3.py` (Python 3.14.6, CPython):
- После создания `data = [1, 2, 3]`: `getrefcount(data) == 1`.
- После `alias = data`: счетчик `2`.
- После `container = [data]`: счетчик `3`.
- После `del alias`: счетчик `2`.
- После `container.clear()`: счетчик `1`.

#### Пояснения:
- В классических руководствах по Python (≤ 3.12) указывается, что `sys.getrefcount()` возвращает значение **на 1 больше** реального, так как вызов функции сам по себе создавал временную ссылку на аргумент. В **Python 3.14** (CPython) это поведение изменилось: передача аргументов оптимизирована, временная ссылка больше не создаётся внутри функции, и счётчики внутри функции показывают **фактическое** число сильных ссылок (1, 2, 3, 2, 1).
- **Инструкции, увеличивающие счётчик:** Присваивание имени (`b = a`), передача в функцию, помещение в контейнеры (списки, словари, кортежи).
- **Инструкции, уменьшающие счётчик:** `del name`, переназначение имени на другой объект, удаление из контейнера (`list.remove`, `dict.pop`), выход из локальной области видимости.
- `del alias` удаляет связывание имени `alias` из текущего пространства имён, уменьшая счётчик ссылок на объект. Сам объект не удаляется до тех пор, пока его счётчик ссылок не станет равным 0.

---

### Слабые ссылки (`weakref`)
* **Слабая ссылка (`weakref.ref`)** позволяет ссылаться на объект, не увеличивая его счетчик ссылок. Когда уничтожаются все сильные ссылки, объект немедленно удаляется, а слабая ссылка начинает возвращать `None`.
* **Практическое применение:** Кэширование тяжелых объектов, реестры наблюдателей (Observer Pattern), предотвращение циклических сильных ссылок в сложных графах и деревьях.

### Ответы на вопросы для анализа (Задание 3)
1. **При каком условии подсчет ссылок позволяет освободить объект?**  
   Объект освобождается мгновенно, когда счетчик сильных ссылок на него падаёт до нуля (`refcount == 0`).
2. **Всегда ли освобождение Python-объекта означает немедленный возврат памяти операционной системе?**  
   Нет. CPython использует собственный менеджер памяти (`PyMalloc`) для объектов размером до 512 байт. Память возвращается во внутренние пулы и арены CPython для повторного использования под новые объекты и может не отдаваться ОС немедленно.
3. **Чем сильная ссылка отличается от слабой?**  
   Сильная ссылка удерживает объект в памяти (увеличивает refcount). Слабая ссылка дает доступ к объекту, но не препятствует его уничтожению сборщиком мусора, когда сильные ссылки исчезают.

## 5. Задание 4. Циклические ссылки и сборщик мусора (`gc`)

### Эксперимент 1. Простая циклическая ссылка и `gc.collect()`
```python
first = []
second = []
first.append(second)
second.append(first)
del first, second
```
* **Прогноз:** После `del first, second` счётчики ссылок каждого списка останутся ненулевыми (каждый список хранит ссылку на другой). Простой подсчёт ссылок не освободит их. Циклический GC должен найти и собрать оба объекта.
* **Результаты `task_4.py`:**
  - `gc.isenabled()`: `True`.
  - Пороги поколений: `(2000, 10, 10)`.
  - Запуск `gc.collect()` после `del first, second` возвращает `2` собранных объекта.
* **Объяснение:** Даже после `del first, second` счётчик ссылок каждого списка оставался равным 1 (`first` хранил ссылку на `second`, `second` — на `first`). Подсчёт ссылок не способен освободить такие структуры. Циклический GC CPython находит недостижимые изолированные группы объектов путём вычитания внутренних ссылок.

#### Назначение поколений сборщика мусора:
CPython делит объекты на 3 поколения (Gen 0, Gen 1, Gen 2), основываясь на гипотезе о том, что большинство объектов «умирают молодыми». Новые объекты попадают в Gen 0. Сборка Gen 0 происходит часто и быстро. Выжившие объекты перемещаются в старшие поколения, проверяемые значительно реже, что резко снижает накладные расходы GC.

---

### Эксперимент 2. Отключение и ручной запуск сборщика мусора

* **Прогноз:** После `gc.disable()` автоматическая сборка отключается. Создание 5 пар циклически связанных словарей (`a["next"] = b`, `b["prev"] = a`) и удаление внешних ссылок (`del cycles`) не освободит память автоматически — счётчики ссылок у словарей ненулевые из-за взаимных связей. Ручной `gc.collect()` должен собрать все изолированные циклы.
* **Фактический результат:**
  - `gc.isenabled()` после `gc.disable()`: `False`.
  - `gc.collect()` вернул `8` объектов (5 пар × 2 словаря — часть объектов уже была собрана при предыдущих вызовах).
  - После `gc.enable()`: `gc.isenabled()` снова `True`.
* **Объяснение:** Выключенный GC означает, что циклические изолированные объекты накапливаются в памяти и не удаляются автоматически. Только явный вызов `gc.collect()` находит и очищает такие структуры. Это важно для серверных процессов, где GC иногда временно отключают для снижения задержек (latency spikes), — после критической секции его необходимо обязательно включить обратно через `gc.enable()`.

### Итоговый анализ: 3 способа уменьшения потребления памяти
1. **Использование генераторов и ленивых вычислений вместо материализованных списков:**

2. **Использование `__slots__` в пользовательских классах:**
   - *Связь с Экспериментом 3 и 5.1:* По умолчанию экземпляры классов хранят атрибуты в `__dict__` (занимающем от 100+ байт на объект). Использование `__slots__` исключает `__dict__` и снижает расход памяти на каждый экземпляр на ~60-70%.
3. **Использование слабой ссылки `weakref` для кэшей и реестров:**
   - *Связь с Экспериментом 3.3:* Использование `weakref.WeakValueDictionary` предотвращает утечки памяти, автоматически удаляя неиспользуемые объекты кэша сразу после того, как они перестают быть нужными в основной программе.

## 7. Заключение: Самые опасные ошибки при работе с изменяемыми объектами

1. **Непреднамеренное совместное использование изменяемых объектов через простое присваивание (`b = a`):** Изменение `b` неявно портит состояние `a`, что приводит к трудноотлавливаемым багам в больших системах.
2. **Использование изменяемых объектов в качестве значений по умолчанию для аргументов функций (`def fn(arg=[]):`):** Список создается 1 раз при компиляции функции и становится общим для всех последующих вызовов.
3. **Ошибочное создание многомерных массивов через дублирование списков (`[[0]*3]*3`):** Все строки матрицы становятся одной и той же ссылкой в памяти.
4. **Забытые циклические ссылки при отключенном или заблокированном GC:** Приводит к неконтролируемым утечкам памяти в долговременных процессах (демонах, веб-серверах).
